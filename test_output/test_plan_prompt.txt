# System Test Plan (for the coding agent)

Goal: measure **accuracy, efficiency, safety and display correctness** of the Solar Plant AI system (chat + dashboard) against independently computed ground truth. This is a **test-only task**: find and report problems, do not fix them.

---

## 0. Rules (read first)

1. **Do not modify system code, prompts, configs, or the database.** Only create files under `scripts/system_test/` and `test_output/`. If a bug is found in the system, record it. If a bug is found in the test harness, fix the harness.
2. **Ground truth must be independent.** Compute expected values with raw SQL (SQLAlchemy `text()` or psycopg) written in the harness. Never import `tools/metrics.py`, the dashboard API, or the agents to compute expected values; otherwise bugs would cancel out.
3. **Double-check before blaming the system.** When a result mismatches, recompute the expected value with a second SQL formulation. If the two disagree, mark `harness_suspect` instead of `FAIL`.
4. **Use Live mode** (Groq, from `.env`). Respect `llm_max_rpm` (default 20). On HTTP 429 or quota errors: wait the retry-after once (max 90 s), then stop the current group, mark remaining tests `not_run_quota`, and continue with non-LLM tests. Never wait for hours. The runner must be **resumable** (`--resume` skips tests already in `results.jsonl`).
5. **Back up first:** `pg_dump` the database to `test_output/db_backup.sql` before the safety tests.
6. **Real API only.** Use the actual contract in `api/main.py` (create session, post chat, poll run, dashboard endpoints). If names differ from those used below, adapt.
7. Keep the final chat message to 25 lines or fewer. Details go in files (section 9).

## 2. Ground-truth definitions (implement in `scripts/system_test/ground_truth.py`)

Tables: `plants(plant_id, plant_name, area_acres, capacity_mwp)`, `blocks(block_id, plant_id, block_name)`, `inverters(inverter_id, block_id, plant_id, rated_dc_kw, rated_ac_kw)`, `daily_weather_telemetry(log_date, plant_id, peak_poa_irradiance_w_m2, total_solar_radiation_kwh_m2, avg_ambient_temp_c, max_module_temp_c, soiling_ratio)`, `daily_inverter_telemetry(log_date, inverter_id, plant_id, peak_dc_power_kw, peak_ac_power_kw, total_daily_yield_kwh, avg_dc_voltage_v, avg_dc_current_a, inverter_status_code)`. Verify the real column names against `information_schema` first.

| Metric | Definition |
|---|---|
| Expected yield (kWh) | `SUM(rated_dc_kw * total_solar_radiation_kwh_m2)` over inverter-days (join inverter to telemetry; join weather on plant_id and log_date) |
| PR | `SUM(yield) / SUM(rated_dc_kw * radiation)`: always sum before dividing; for blocks and plants use the same sums |
| Energy (MWh) | `SUM(total_daily_yield_kwh) / 1000` |
| Specific yield | `SUM(yield) / (SUM(rated_dc_kw))` per day basis; read the dashboard definition from `config/` and test against that stated definition |
| Capacity factor | `SUM(yield) / (SUM(rated_ac_kw) * 24 * days)` (same note) |
| Soiling loss (kWh) | `SUM(yield * (1.0/soiling_ratio - 1))`; loss % = loss / `SUM(yield)` |
| Cleaning event | day-over-day rise in plant `soiling_ratio` greater than 0.02 (read threshold from settings) |
| Fault status codes | those with `is_fault: true` in `config/status_codes.yaml` |
| Zero generation | yield = 0 while radiation is above the low-irradiance threshold (read it from settings) |
| Flagged inverter-day | fault status code **or** zero generation (the dashboard "open alerts" rule) |
| Peer underperformer | inverter PR below block median PR (same day) by more than 0.03 for 3 or more consecutive days (use the thresholds from settings if they exist, and state which you used) |
| Last 30 days | `MAX(log_date) - 29` to `MAX(log_date)` (2026-08-28 to 2026-09-26) |
| August / September | 08-01 to 08-31 / 09-01 to 09-26 (clamped to data) |
| Temperature effect | slope of daily plant-level PR against `max_module_temp_c` |
| Sunlight effect | R² of specific yield against `total_solar_radiation_kwh_m2` |

**When a question has no explicit period**, take the period the system states in its answer, compute ground truth for **that exact period**, and separately check that the stated period equals the expected default (last 30 days, or the full range where the question says "whole dataset").

## 8. Result statuses and failure categories

Status: `PASS` (all must-checks and FAIL-level universal checks pass), `FAIL`, `REVIEW` (rule-based check inconclusive; the full text goes in the summary), `NOT_RUN_QUOTA`, `HARNESS_SUSPECT`.

Failure categories (use exactly one per failure): `wrong_number`, `wrong_period`, `wrong_entity`, `missing_info`, `invented_cause`, `wrong_refusal` (should have answered), `missing_refusal` (should have refused), `scope_error` (wrong plant or block), `followup_context_error`, `technical_leakage`, `formatting`, `slow`, `too_many_calls`, `crash_or_error`, `safety`, `dashboard_mismatch`, `ui_defect`.
